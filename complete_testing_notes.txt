SOFTWARE TESTING – COMPLETE NOTES
1. Introduction to Software Testing
What is Testing?
Software Testing is the process of executing a program/application with the intention of finding defects or bugs.
In simple terms:
Testing = Comparing expected results with actual results.
Testing helps verify whether the application satisfies the specified requirements.
Testing is also associated with:
* Verification – Are we building the product right?
* Validation – Are we building the right product?

2. Types of Applications
Applications can be broadly classified into:
1. Windows / Standalone Applications
Applications that run independently on a computer.
Examples:
* Calculator
* Notepad
* MS Word
2. Web Applications
Applications that are accessed through a web browser.
Examples:
* Gmail
* Amazon
* Flipkart
3. Client-Server Applications
Applications where a client communicates with a server to exchange data.
Example:
* Banking application
4. Three-Tier Applications
A three-tier application generally contains:
Browser → Application Server → Database
Example:
User → Browser → Application → Database
Each layer has a separate responsibility.

3. Testing vs Debugging
Testing	Debugging
Done mainly by testers	Done mainly by developers
Main intention is to find defects	Main intention is to identify and fix the cause of defects
Testing executes the application to find failures	Debugging may involve step-by-step execution of code
Tester reports defects	Developer analyzes and fixes defects
Part of STLC	Mainly part of development/SDLC activities
Example
If a calculator gives 10 instead of 15:
* Tester: Identifies and reports the problem.
* Developer: Debugs the code to find the reason and fixes it.

4. Bug vs Defect
Bug
A bug is a deviation of the actual behavior from the expected requirement.
The term bug is commonly used by testers during the testing phase.
Defect
A defect is a deviation from the specified requirements/specifications.
The term defect is commonly used during development activities.
Simple Difference
Requirement → Expected Result → Actual Result
If:
Expected ≠ Actual → Defect/Bug

5. Necessity / Need for Testing
Testing is necessary to:
1. Gain customer confidence
2. Improve product quality
3. Avoid extra costs
4. Reduce business risks
5. Optimize business operations
6. Ensure requirements are satisfied
7. Prevent failures after release
8. Improve customer satisfaction

6. Psychology / Motto of Testing
The main objectives of testing are:
1. Identify defects
    * Verify business requirements, functional requirements and SRS.
2. Improve product quality
    * Finding defects helps developers improve the product.
3. Ensure requirements are satisfied
    * Verify that business and user requirements are fulfilled.
4. Provide information about defects
    * Testers report defects so that they can be analyzed and corrected.
Important Point
A tester's goal is not to prove that the application has no bugs. The goal is to find defects before the customer does.

10. Seven Principles of Software Testing
There are 7 important principles of software testing.
1. Testing Shows the Presence of Defects
Testing can show that defects exist in a system.
However, testing cannot prove that the application is completely defect-free.

2. Exhaustive Testing is Impossible
It is impossible to test every possible input and combination.
Therefore, testers use techniques such as:
* Equivalence Partitioning
* Boundary Value Analysis
* Decision Tables
* State Transition Testing
* Error Guessing

3. Early Testing
Testing should start as early as possible in the SDLC.
Finding defects early is generally cheaper and easier than finding them after release.
Early testing saves time and money.

4. Defect Clustering
A small number of modules generally contain a large number of defects.
Therefore, testers should focus more attention on defect-prone modules.

5. Pesticide Paradox
If the same tests are repeated again and again, they may eventually fail to identify new defects.
Therefore, test cases should be reviewed and updated regularly.

6. Testing is Context Dependent
Testing techniques depend on the type of application.
For example:
* Banking application → Security and transaction testing are important.
* Gaming application → Performance and usability are important.
* Healthcare application → Accuracy and reliability are very important.

7. Absence-of-Errors is a Fallacy
Even if no defects are found, the application may still fail to satisfy the customer's actual needs.
Therefore:
No detected defects ≠ Perfect software

11. Quality Assurance vs Quality Control

QA activities are mainly associated with process improvement and SDLC activities.
Examples:
* Process definition
* Standards
* Reviews
* Audits
* Process improvement

Quality Control (QC)
QC is product-oriented.
It focuses on identifying defects in the actual product.
Testing is an important QC activity.
Simple Difference
QA → Prevent defects
QC → Find defects

White Box Testing is testing an application using knowledge of its internal structure, logic, code and implementation.
It is generally performed by developers or technical testers.
Major types:
1. Unit Testing

14. Unit Testing
Unit testing is testing the smallest testable unit/component of source code independently.
Examples of Unit Testing Techniques
1. Basis Path Testing
2. Statement Coverage
3. Branch/Decision Coverage
4. Loop Coverage
5. Cyclomatic Complexity

Cyclomatic Complexity
Cyclomatic complexity is a measure of the number of independent paths in a program.
It helps determine the minimum number of independent paths that should be tested.

DAY 2 – BLACK BOX TESTING
16. Black Box Testing
Black Box Testing is testing an application without knowing or using its internal code/implementation.
The tester focuses on:
* Inputs
* Outputs
* Requirements
* Functional behavior
It is also called specification-based testing.
Major Types
1. Functional Testing
2. Non-Functional Testing

17. Black Box Test Design Techniques
Important Black Box testing techniques are:
1. Equivalence Partitioning
2. Boundary Value Analysis
3. Decision Table Testing
4. State Transition Testing
5. Error Guessing

18. Equivalence Partitioning
Equivalence Partitioning divides input data into different groups/classes where the system is expected to behave similarly.
Example
Suppose age should be between 18 and 58.
We can divide the inputs into:
* Below 18 → Invalid
* 18–58 → Valid
* Above 58 → Invalid
Instead of testing every possible age, we select representative values from each partition.

19. Boundary Value Analysis (BVA)
Boundary Value Analysis focuses on values at and around the boundaries of an input range.
For a valid range:
Minimum = 18
Maximum = 58
Around Minimum
Value	Expected Result
17 (Min - 1)	Invalid
18 (Min)	Valid
19 (Min + 1)	Valid
Around Maximum
Value	Expected Result
57 (Max - 1)	Valid
58 (Max)	Valid
59 (Max + 1)	Invalid
BVA Formula
Test values around:
Min - 1, Min, Min + 1
Max - 1, Max, Max + 1

21. Decision Table Testing
A Decision Table is a testing technique used when the output/action depends on multiple conditions.
It represents:
Conditions → Actions
It is also commonly called a Cause-Effect representation/table in basic testing discussions.
Example – Login
Conditions:
* Username correct?
* Password correct?
Actions:
* Allow login
* Display error
Username	Password	Action
Correct	Correct	Login successful
Correct	Wrong	Show password error
Wrong	Correct	Show username error
Wrong	Wrong	Show login error
Decision tables are useful when there are multiple combinations of conditions.

22. State Transition Testing
State Transition Testing is used when the behavior of an application depends on its current state and previous actions/events.
The application moves from one state to another based on an event/action.
Example – ATM Card
Possible states:
1. Card Inserted
2. PIN Entered
3. PIN Verified
4. Transaction Selected
5. Transaction Completed
6. Card Ejected
Example – Login Account
States:
Active → Wrong Password → Locked
After several incorrect login attempts, the account may move from an Active state to a Locked state.

23. Error Guessing
Error Guessing is a testing technique where testers use their experience and knowledge of common mistakes to predict where defects may occur.
Common examples:
* Entering blank values
* Entering special characters
* Entering invalid formats
* Entering very large values
* Entering negative values
* Repeatedly clicking buttons
* Leaving mandatory fields empty
It is largely based on tester experience.

29. Test Case
A Test Case contains detailed steps used to verify a particular functionality.
A typical test case contains:
* Test Case ID
* Test Scenario
* Test Steps
* Test Data
* Expected Result
* Actual Result
* Status (Pass/Fail)
Example
Test Case: Verify login with valid credentials.
Steps:
1. Open login page.
2. Enter valid username.
3. Enter valid password.
4. Click Login.
Expected Result: User should be successfully logged in.
Actual Result: Actual behavior observed during execution.
Status: Pass / Fail

30. Characteristics of Good Test Cases
A good test case should be:
1. Simple
2. Clear
3. Easy to understand
4. Readable
5. Independent where possible
6. Maintainable
7. Reusable where appropriate
8. Non-duplicative
9. Traceable to requirements
10. Able to verify the intended functionality
Test cases should be written clearly enough that another tester can understand and execute them.

31. Defect Classification
Defects are commonly classified based on Severity and Priority.

32. Severity
Severity describes how seriously a defect affects the functionality or business of the application.
Severity is generally assigned by the QA/Tester.
Types of Severity
1. Blocker
2. Critical
3. Major
4. Minor
Examples
Blocker: Application cannot proceed or testing is blocked.
Critical: Major functionality is severely affected.
Major: Important functionality is not working correctly.
Minor: Small issue with limited functional impact.

33. Priority
Priority indicates how urgently a defect should be fixed.
Priority is generally decided by the development/product team, often with input from QA and business stakeholders.
Common Priority Levels
* High – P0
* Medium – P1
* Low – P2
Priority is about urgency, while severity is about impact.

34. Severity vs Priority
Severity	Priority
Measures impact of defect	Measures urgency of fixing defect
Mainly concerned with functionality/business impact	Mainly concerned with business/release importance
Usually assigned by QA	Usually decided by development/product/business stakeholders
Blocker/Critical/Major/Minor	High/Medium/Low
Example: Low Severity + High Priority
A spelling mistake in the company name on the homepage may have low functional severity but high priority because it is highly visible to customers.
Example: High Severity + Low Priority
A serious issue in a rarely used legacy feature might have high technical severity but lower business priority, depending on the product context.

35. Defect / Bug Life Cycle
A tester's responsibility is generally to identify and report a defect. The developer analyzes and fixes it.
Typical Defect Life Cycle
New → Assigned → Open → Fixed → Retest/Verified → Closed
There can also be alternative statuses.

1. New
Tester identifies and reports the defect.

2. Assigned
The defect is assigned to the responsible developer/team.

3. Open
Developer starts analyzing the defect.

4. Fixed
Developer fixes the defect and provides the build for testing.

5. Verified / Retest
Tester retests the defect.
If the issue is fixed:
→ Closed
If the issue still exists:
→ Reopened

6. Closed
Tester confirms that the defect has been fixed successfully.

36. Other Defect Statuses
Rejected
The reported issue is not considered a valid defect.
Duplicate
The same defect has already been reported.
Deferred
The defect is genuine, but the team decides to fix it in a future:
* Sprint
* Release
* Version

37. Requirement Traceability Matrix (RTM)
RTM = Requirement Traceability Matrix
RTM is used to establish a relationship between requirements and test cases.
Its main purpose is to ensure that requirements are covered by testing.
Types of Traceability
1. Forward Traceability
Requirements → Test Cases
It ensures that every requirement has corresponding test cases.

2. Backward Traceability
Test Cases → Requirements
It ensures that every test case is associated with a requirement.

3. Bi-Directional Traceability
Requirements ↔ Test Cases
It combines both forward and backward traceability.
Simple Representation
Forward:
Requirement → Test Case
Backward:
Test Case → Requirement
Bi-Directional:
Requirement ↔ Test Case

1. Testing Terminologies
Smoke Testing
* Testing the stability of a new build.
* Developer gives .exe/setup.exe build.
* Build is deployed in the testing environment.
* Tester checks basic functions.
* Example: Login, Logout, application launch.
Smoke Testing → Build stability

Sanity Testing
* Checking important/critical functionalities of an application.
* Usually done after minor changes/fixes.
Sanity Testing → Critical functionality

Ad-hoc Testing
* Testing the application using predefined ideas without following rules or predefined test cases.
* Mainly depends on tester experience.

Exploratory Testing
* Testing an application by exploring it and learning about it while testing.
* Useful when tester has limited domain knowledge.

Monkey Testing
* Testing the application randomly due to limited time or to find unexpected failures.
* Commonly used for games/software.

Gorilla Testing
* Testing a particular module/functionality repeatedly and intensively.

2. Regression Testing
Testing existing functionality after changes to ensure the new/modified functionality has not affected existing functionality.
Regression → Old functionality should not break

3. Retesting
* Developer fixes a reported defect.
* Tester tests the same functionality again.
* Checks whether Expected = Actual.
Retesting → Checking whether the bug is fixed

Regression vs Retesting
Retesting	Regression
Checks whether defect is fixed	Checks whether existing features are affected
Same failed functionality	Existing functionality

Selenium Locators

There are 8 locators:
1. ID
2. Name
3. XPath
4. Tag Name
5. Link Text
6. Partial Link Text
7. CSS Selector
8. Class Name
1. ID
* ID is a locator used to find an element on a webpage.
* It is the fastest way to identify an element when a unique ID is available.
2. Name
* If the ID locator is not present, we can use the Name locator.
* The Name locator works similarly to the ID locator but is comparatively slower.
3. XPath
XPath stands for XML Path.
There are two types of XPath:
1. Absolute XPath
2. Relative XPath
Absolute XPath
* Absolute XPath starts from the HTML root node.
* It is represented by a single /.
Relative XPath
* Relative XPath is represented by //.
* It searches for the locator value from the parent or relevant node.
